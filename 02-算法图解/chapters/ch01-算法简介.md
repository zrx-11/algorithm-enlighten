# 第 1 章：算法简介

- **难度**：★☆☆ | **预估学时**：1.5 小时 | **前置**：无（只需会基本代数，如 f(x)=x×2，f(5)=10）

## 学习目标

学完本章，你能：

1. 说出二分查找比简单查找快在哪里，并解释"每次排除一半"为什么对应 log₂n 步。
2. 用大O表示法判断一个常见操作的运行时间（O(log n) / O(n) / O(n²) / O(n!) 等）。
3. 复述"大O表示法描述的是最糟情况下的操作数增速，而不是秒数"。

## 一句话核心

**好的算法不是"更快"，而是"当数据变多的时候，耗时涨得慢得多"——二分查找把 n 步变成 log₂n 步，大O表示法就是用来比较这种"涨速"的记号。**

## 零基础讲解

### 概念 1：二分查找（难度：基础）

**二分查找（binary search）**：一种只适用于**有序列表**的查找算法。你每次猜中间的元素，根据"猜大了还是猜小了"砍掉一半范围，而不是逐个排查。

**类比**：猜 1~100 的数字。傻办法是从 1 逐个往上猜（最坏要猜 99 次）；聪明办法是先猜 50——如果"小了"，就知道 1~50 全部排除；再猜 75……每次都把范围砍半。

**实例（可复核）**：在 1~100 中猜数字 99。

| 次数 | 猜测值 | 结果 | 剩余范围 |
|---|---|---|---|
| 1 | 50 | 小了 | 51~100（砍半） |
| 2 | 75 | 小了 | 76~100 |
| 3 | 88 | 小了 | 89~100 |
| 4 | 94 | 小了 | 95~100 |
| 5 | 97 | 小了 | 98~100 |
| 6 | 99 | 对了 | —— |

不管我心里想的是哪个数字，**7 次之内必中**，因为 2⁷=128>100。推广：含 n 个元素的有序列表，二分查找最多 **log₂n 步**；简单查找最多 n 步。

**Python 代码（原书示例，已适配现代 Python）**：

```python
def binary_search(list, item):
    low = 0                      # 查找范围的下界
    high = len(list) - 1         # 查找范围的上界

    while low <= high:           # 范围还没缩到只剩一个元素
        mid = (low + high) // 2  # 中间位置（// 整除，向下圆整）
        guess = list[mid]        # 猜中间这个元素
        if guess == item:        # 猜对了，返回位置
            return mid
        if guess > item:         # 猜大了，上界收到 mid 左边
            high = mid - 1
        else:                    # 猜小了，下界放到 mid 右边
            low = mid + 1
    return None                  # 范围耗尽，没找到

my_list = [1, 3, 5, 7, 9]
print(binary_search(my_list, 3))    # => 1（索引从 0 开始，3 在第 2 个位置）
print(binary_search(my_list, -1))  # => None（None 表示"没有找到"）
```

### 概念 2：对数 log（难度：基础）

**对数（logarithm）**：幂运算的逆运算。log₂8 问的是"多少个 2 相乘等于 8"，答案是 3，因为 2³=8。本书里 log 一律指 log₂。

- 8 个元素 → 最多查 log₂8 = 3 次
- 1024 个元素 → 最多查 log₂1024 = 10 次
- 10 亿（40 亿）个元素 → 最多查约 30（32）次

**类比**：对数像"对折次数"。一张纸对折 10 次有 1024 层——你要从 1024 层里找某一层，只需对折式地定位 10 次。（失效边界：这个类比只解释 2 的幂；非 2 的幂时取向上取整，如 log₂100≈7。）

### 概念 3：大O表示法（难度：进阶）

**大O表示法（Big O notation）**：一种描述"算法操作数随输入规模 n 如何增长"的记号。它衡量的是**增速**，不是秒数；描述的是**最糟情况**。

原书 NASA 例子：Bob 以为列表 100 个元素时简单查找（100 毫秒）比二分查找（7 毫秒）只慢 15 倍，于是火箭着陆选了简单查找。实际上列表有 10 亿个元素时，简单查找要 10 亿毫秒 ≈ **11 天**，而二分查找只要约 30 毫秒——差 3300 万倍。结论：**只看当前数据量的耗时没用，要看数据变多后耗时涨多快。**

常见 5 种大O运行时间（从快到慢）：

| 大O | 名称 | 代表算法 | n=1024 时的操作数 |
|---|---|---|---|
| O(log n) | 对数时间 | 二分查找 | 10 |
| O(n) | 线性时间 | 简单查找 | 1024 |
| O(n log n) | —— | 快速排序（第4章） | ~10000 |
| O(n²) | 平方时间 | 选择排序（第2章） | ~100 万 |
| O(n!) | 阶乘时间 | 旅行商问题蛮力解 | 天文数字 |

**实例（旅行商问题）**：5 个城市有 5!=120 种排列；6 个城市 720 种；7 个城市 5040 种；100 个城市时算到太阳熄灭也算不完。这类问题叫 **NP 完全问题**（第8章展开）。

## 类比与实例

- **类比**：大O像"堵车的增长趋势"。你问从家到公司要多久，我回答"正常 20 分钟"没意义——该回答"每多 1000 辆车，路程多堵多少分钟"。大O就是后者。
  - 失效边界：大O忽略常数（如每步实际 1 毫秒还是 1 秒）。当两种算法大O相同的时候，常数才有意义（第4章会回到这一点）。
- **实例（可复核）**：含 128 个名字的有序列表，二分查找最多几步？log₂128 = 7 步；列表翻倍成 256 个名字，最多 8 步。每翻倍一次，只多 1 步——这就是"对数增速"的手感。

## 常见误解

- **别以为"二分查找更快"是因为写代码优化得好**——实际上它快在算法思路：每次排除一半。代码再烂的二分查找，只要思路对，也是 O(log n)。
- **别以为大O表示法说的是秒数**——实际上它说的是操作数的增速，连"常数"都忽略（O(2n) 简写为 O(n)）。
- **别以为"找到了 Adit 一次就中，所以简单查找是 O(1)"**——实际上大O看最糟情况：找最后一个人得翻完整本电话簿，所以简单查找是 O(n)。O(1) 是"保证不会比这更差"的上限。

## 自测题（答案）

1. （单选）在含 256 个元素的有序列表中用二分查找，最多需要多少次？A. 256　B. 8　C. 16　D. 128
   （答案：B；解析：log₂256 = 8，因为 2⁸ = 256。每翻倍一次只多一步。）
2. （单选）在无序的人名列表里按电话号码反查某人（必须翻遍整本电话簿），运行时间是？A. O(log n)　B. O(n)　C. O(n²)　D. O(1)
   （答案：B；解析：这是原书练习 1.4——没有有序前提就用不了二分查找，只能逐个排查，是线性时间 O(n)。）
3. （填空）旅行商问题要试遍所有排列，其运行时间为 O(____)。
   （答案：n!（阶乘）；解析：5 城 120 种、6 城 720 种、7 城 5040 种，每加一城路线数乘上一个更大的数，即 n 的阶乘。）
4. （简答）为什么 Bob 用简单查找引导火箭着陆是错的？
   （答案：他在 n=100 时测得只慢 15 倍；但 n=10 亿时简单查找要约 11 天而二分查找只要 30 毫秒。大O不同，常数的小优势在 n 变大后毫无意义。）

## 复习锚点

- 有序列表上：简单查找 O(n)，二分查找 O(log n)；每翻倍数据量，二分查找只多一步。
- 大O = 操作数的增速（最糟情况），不是秒数；常见档：O(log n) < O(n) < O(n log n) < O(n²) < O(n!)。
- O(n!) 的旅行商问题目前没有快解，只能求近似解（第8章）。
